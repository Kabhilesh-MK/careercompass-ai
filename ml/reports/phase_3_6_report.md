### 1. OBJECTIVE

The primary objective of Phase 3.6 was to replace the legacy mock career prediction UI with a thin client integration connected directly to the production FastAPI ML inference service established in Phase 3.5.

The complete production lifecycle is now:
```
Student Skills
      ↓
Frontend Input Validation (checks non-empty skills list)
      ↓
GET /api/v1/predictions/career/skills (fetches authoritative 29-feature vocabulary)
      ↓
Student Selects / Enters Skills (binary token representation)
      ↓
POST /api/v1/predictions/career (JSON payload: { "skills": [...] })
      ↓
FastAPI Executes Candidate H Inference (RandomForestClassifier)
      ↓
Frontend Receives Typed ML Response (CareerPredictionResponse)
      ↓
React Renders Real Predictions, Probabilities & Input Auditing
```

### 2. FRONTEND ARCHITECTURE CHANGES

The frontend architecture was upgraded to transition the client from a mock-driven interface to a thin, reactive ML consumer:

1. **Typed Service Layer**: Created `src/services/api/mlInference.ts` encapsulating all HTTP communication, response parsing, and error sanitization.
2. **Authoritative Vocabulary**: Skill chips and selection controls dynamically fetch and display the canonical 29-feature vocabulary directly from the FastAPI endpoint.
3. **Dynamic Prediction View**: `src/pages/career/CareerPrediction.tsx` was rewritten to eliminate static mock objects (`DEMO_PREDICTION_CURRENT`). The page renders dynamic predictions, ranked probability distributions across all 4 tracks, unknown skill alerts, and technical governance metadata.
4. **State Persistence Synchronization**: `src/context/AppStateReducer.ts` and `src/types/appState.ts` were expanded with a `RECORD_PREDICTION` action that writes real ML inferences into persistent `localStorage` while preserving immutability.
5. **Prediction History Distinction**: `src/pages/predictions/PredictionHistory.tsx` was enhanced to distinguish `REAL ML INFERENCE` records from legacy `LEGACY DEMO` audit items.
6. **Dashboard Connection**: `src/pages/dashboard/Dashboard.tsx` was connected to display the latest verified real ML prediction when available, or an explicit `AWAITING LIVE ML RUN` status when no prediction has been executed.

### 3. TYPED API CLIENT (`src/services/api/mlInference.ts`)

A strongly typed API client was implemented with strict error handling, schema validation, and zero fake-data fallbacks:

```typescript
export interface CareerPredictionRequest {
  skills: string[];
}

export interface CareerProbability {
  career_track: string;
  probability: number;
}

export interface CareerPredictionResponse {
  prediction: {
    career_track: string;
    probability: number;
  };
  alternatives: CareerProbability[];
  probabilities: CareerProbability[];
  input: {
    recognized_skills: string[];
    unknown_skills: string[];
  };
  model: {
    version: string;
    model_type: string;
    feature_configuration: string;
  };
  explanation?: unknown;
}

export interface SkillVocabularyResponse {
  skills: string[];
  count: number;
  model_version?: string;
}

export interface ModelInfoResponse {
  model_version: string;
  model_type: string;
  feature_configuration: string;
  feature_count: number;
  classes: string[];
  training_samples: number;
  threshold_policy: string;
}
```

Functions implemented:
- `getCareerSkillVocabulary(): Promise<SkillVocabularyResponse>`: Queries `GET /api/v1/predictions/career/skills`.
- `predictCareer(skills: string[]): Promise<CareerPredictionResponse>`: Sends `POST /api/v1/predictions/career`.
- `getModelInfo(): Promise<ModelInfoResponse>`: Queries `GET /api/v1/model/info`.

### 5. PREDICTION INTEGRATION

Dynamic ML prediction triggers upon user command:
- Selected skills are formatted as a clean string array (`string[]`).
- Sent via HTTP POST to `/api/v1/predictions/career`.
- Duplicate submissions are blocked during network transfer via button disabling and animated state indicators.
- The UI binds directly to:
  - `response.prediction` for the primary recommended track.
  - `response.probabilities` for the full 4-track distribution (preserving backend sorting).
  - `response.input` for input auditing.
  - `response.model` for runtime governance parameters.

---

### 6. STATE MANAGEMENT

- Prediction results are dispatched to the global React state via `RECORD_PREDICTION`.
- Each record persists:
  - `id`: Unique timestamped ID (`pred-ml-${Date.now()}`).
  - `date`: Current ISO date stamp.
  - `predictedCareer`: Canonical track name.
  - `confidenceEstimate`: Model probability rounded to integer percentage.
  - `isRealMl`: `true`.
  - `submittedSkills`: Raw skill tokens submitted.
  - `recognizedSkills`: Array of tokens recognized by the 29-feature vocabulary.
  - `unknownSkills`: Array of tokens not present in vocabulary.
  - `probabilities`: Complete 4-class probability distribution.
  - `modelType`: `'RandomForestClassifier'`.
  - `assessmentVersion`: `'phase3.4'`.
- All updates are automatically serialized to browser `localStorage` under `careercompass_state_v2`.

### 7. ERROR HANDLING

The API client and UI handle all error scenarios gracefully without leaking internal stack traces or Python filesystem paths:
- **Network Outage / Service Down**: Caught as network failure; surfaces user-safe message:  
  `"Career prediction is temporarily unavailable. Please make sure the ML service is running at http://127.0.0.1:8000 and try again."`
- **HTTP 422 (Validation Error)**: Empty input or missing parameters trigger clean validation messages (`"Please select or enter at least one skill before requesting a prediction."`).
- **HTTP 503 (Model Not Ready)**: Surfaces: `"Career prediction is temporarily unavailable. The ML model service is initializing or not ready."`
- **HTTP 500 (Internal Inference Failure)**: Surfaces generic server notification without Python file paths or exception tracebacks.
- **Strict Prohibition**: Under no error condition does the client catch an exception and return mock prediction data.

### 9. UNKNOWN SKILL HANDLING

Incoming skill tokens not recognized by Candidate H's 29-skill vocabulary are processed transparently:
- The backend partitions inputs into `recognized_skills` and `unknown_skills`.
- When `unknown_skills.length > 0`, the frontend displays a distinct, non-blocking warning card:
  - **Title**: `"Unknown Skills Detected (N)"`
  - **Chips**: Displays each unknown token with amber tags (e.g. `unknown_skill_xyz`).
  - **Explanation**: `"These skills are not currently part of the ML model vocabulary and did not influence the prediction."`
- The system never converts unknown skills into recognized skills or attributes prediction outcomes to them.

### 17. LIMITATIONS & PHASE 3.7 RECOMMENDATION

#### Current Limitations:
1. **Uncalibrated Probabilities**: As established in Phase 3.4, Candidate H's Random Forest probabilities are uncalibrated tree votes. A probability of 67% indicates ensemble agreement across trees, not a calibrated 67% empirical probability.
2. **Binary Skill Feature Representation**: The model does not consume continuous skill proficiency scores (e.g. 82% Python); presence is strictly binary (0 or 1).
3. **Client-Side History**: Historical prediction entries are persisted in browser `localStorage`. Multi-device persistence requires future backend account synchronization.

#### Phase 3.7 Recommendation:
Proceed to **Phase 3.7: Production Calibration, Feature Explainability (SHAP / TreeExplainer), and End-to-End Persistence**:
1. Evaluate isotonic regression vs Platt scaling calibration specifically for Candidate H across 5-fold cross-validation.
2. Implement backend tree SHAP feature contribution endpoints (`GET /api/v1/predictions/career/explain`) to replace static frontend explanation cards with mathematically grounded feature importance for individual student predictions.
3. Wire user prediction history directly into the backend MongoDB `predictions` collection for authenticated students.
